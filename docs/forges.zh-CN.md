# 连接 Gitee 和 Gitea

[English](forges.md)

GitHub：在插件页的 GitHub 里点「登录 GitHub」，Nod 会显示一次性验证码并打开 GitHub，粘贴验证码后授权即可。Nod 以你的身份工作，能访问你有权限的仓库。如果组织限制了第三方应用，在授权页（或之后在 设置 → Applications）为 Nod 申请访问，由组织管理员批准一次。GitHub Enterprise 需要在自己的实例上注册一个开启 Device Flow 的 OAuth App，并在同一页填写它的 Client ID。Gitee 和 Gitea / Forgejo 都要提供一个访问令牌。Nod 把令牌存在系统钥匙串里，配置文件里不会出现。

在 Nod 里打开「插件 → 代码平台 → 添加账号」，选择平台，填写令牌（Gitea 还要填地址），然后点「自检」确认能登录。可以同时连接多个账号，比如公司的 Gitee 加上个人的 GitHub。

## Gitee（码云）

1. 登录 gitee.com，进入「设置 → 安全设置 → 私人令牌」，生成新令牌。
2. 权限勾选 **user_info**、**projects**、**pull_requests**。
3. 在 Nod 里填写私人令牌；地址留空即为 gitee.com。

Nod 会做这几件事：

- 找出把你设为**审查人员**的、打开状态的 PR。Gitee 没有跨仓库的「请我审查」查询，Nod 会列出你能访问的仓库（最多 500 个，每 10 分钟刷新一次），再逐个查询。在「设置 → 审查范围」里限定仓库，可以减少请求、加快检查。
- 发行内评论和一条总结评论。如果 Gitee 不接受某个行号，这条问题会改成普通评论发出，并注明文件和行号，不会丢。
- 规则全部通过时**审查通过**。

两点限制：

- **审查通过后撤不回**。Gitee 不允许审查人自己撤销，只有管理员能重置。所以如果后续提交有问题，Nod 无法撤销之前的通过，通知里会提示「旧的通过仍然有效」。担心这一点，可以在「设置 → 自动 approve」里只对部分仓库开启。
- CI 状态取的是提交的检查（check runs）。仓库没有配置检查时，按「没有 CI」处理。

令牌是以 `access_token` 参数的形式发给 Gitee 的，这是 Gitee 接口的规定。Nod 会把它从所有报错和日志里去掉。

## Gitea / Forgejo（含 Codeberg）

1. 进入「设置 → 应用 → 管理访问令牌」，新建令牌。
2. 权限选择：**read:user**、**write:repository**、**write:issue**。
3. 在 Nod 里填写实例地址（例如 `https://codeberg.org`）和令牌。

Nod 会找出请求你审查的 PR（需要 Gitea 1.19 或更新版本），以一次 review 的形式发评论，结论为 APPROVED 或 COMMENT。后续提交出问题时，会尝试撤销自己之前给的通过；Gitea 只允许仓库管理员撤销，没有权限时通知里会说明旧的通过仍然有效。CI 状态取的是提交状态（commit status）。

## 排障

- **自检提示 401 或 403**：令牌填错了、已过期，或者权限不够。
- **自检提示连不上**：检查地址是否以 `https://` 开头、能否在浏览器打开，以及代理设置。
- **找到了 PR 但检出失败**：令牌需要能读取这个仓库。检出时令牌只通过环境变量交给 git，不会写进命令行或仓库配置。
- **Gitee 检查很慢**：你能访问的仓库很多。在「审查范围」里写上要审查的仓库，例如 `my-org/*`。
